name: orchestrate
description: Run a multi-step coding task with a plan file, scope-locked workers, Jev routing and gates, and Dryas memory. Use when the user runs $dryas:orchestrate, asks to orchestrate or dispatch workers, or has approved a multi-step plan to execute. Not for single-file fixes or ordinary edits that do not ask for orchestration.

# Orchestrate (Codex)

`<dryas-root>` and `<dryas-py>` are given in the Dryas rules ("Dryas paths:"). If they are missing, the Dryas hooks are not trusted: tell the user to run /hooks in Codex and stop.

0. **Brainstorm first.** Run `$dryas:brainstorm`; plan only from a design the user approved.
1. **Memory.** Call `memory_search` (server `jev`, namespace = main repo folder name) for similar tasks. Write the top 3 as `Past: <what worked> / <what failed>`, or say none were found.
1b. **Preflight: the run must not need the user.** The user decides in brainstorm and plan; from here on nobody is asked. Hooks never prompt during a run: they allow, or deny with a reason the worker can act on. You decide what a worker reports as `NEEDS DECISION`; only what you must not decide alone becomes a `NEEDS USER` item in the end report. Run `"<dryas-py>" -X utf8 "<dryas-root>/jev/preflight.py"` once, before the first `active.json`. It prints `{"ok", "mode", "now", "say"}`. Not ok: do not start; tell the user `say` word for word and stop. Ok: keep `now` as the run start for step 7; pass on a non-empty `say` in one line; tell the user in one plain line that the run has started and they can leave.
2. **Plan as a file.** Create a git worktree for the work with `$dryas:worktree`. One agent per worktree: this session owns it alone; parallel loops each get their own worktree and branch. Write `.orchestrate/PLAN.md` there, one section per task:

   ```
   ## Task <N>: <title>
   Goal: <one sentence>
   Scope:
   - <glob relative to worktree root>
   Done:
   - <verifiable criterion, incl. test command>
   Failing test first: <test file :: test name>
   ```

   Tasks that may run in parallel must not have overlapping scopes. Never commit `.orchestrate/`. If the plan has a `## Risky actions` section, copy it verbatim to the top of `.orchestrate/PLAN.md`, above the first task: during the run those commands are allowed without asking anyone (an exact entry, or a prefix ending in `*`).
3. **Ask Jev per task.** Call `jev_judge` (server `jev`) with state `{task_section, test_file_exists, last_test_run_tail, past_outcomes}` and questions `specific` (noul: is the task specific enough to finish without questions?), `failing_test_exists` (noul) and `needs_stronger_model` (noul: cross-cutting refactor, concurrency- or security-sensitive code?). Each question's `instructions` must stand alone and name state fields in backticks. Below threshold or unavailable: you decide; when you differ from Jev, call `log_override`. When one call covers several tasks, name each question `<question>.<task>` (for example `needs_stronger_model.t3`); $dryas:tune groups calls by the part before the dot.
4. **Test first.** If a failing test does not confidently exist, get it written and failing for the right reason before any implementation.
5. **Dispatch.** Write `.orchestrate/active.json` = `{"active": [<task ids>], "base": {"<N>": "<sha>"}}` (sha = `git rev-parse HEAD` just before that task's first dispatch, kept for re-dispatches); this arms the scope-lock hook. Delete it on every exit path. Give each worker only its own section: `"<dryas-py>" -X utf8 "<dryas-root>/jev/planfile.py" section .orchestrate/PLAN.md <N>` (PowerShell: prefix `& `) plus the plan's Global Constraints section, when the plan document has one, plus the absolute worktree path. Name `<dryas-root>/skills/tdd/SKILL.md` and `<dryas-root>/skills/debug/SKILL.md` in its prompt. Role lessons: right before each dispatch, call `memory_search` (server `jev`) once with namespace `role-<slug>`, query = the task title and task = the dispatch task id, where the slug is `builder` for coder, tester and docs, the review stage's own role for `reviewer-spec`, `reviewer-quality` and `reviewer-minimalist`, and `devils-advocate` for interrogate reviewers. Add the lessons it returns (at most 3, already cut to 600 characters) to the worker's prompt under `Lessons from past <slug> work:`; none returned (or the switch `memory.role_lessons` is off): add nothing. The tool logs which lessons were loaded. A worker may commit its own task only when you allow it in its prompt (explicit paths, a conventional message whose subject ends with `(task <N>)`; its report ends with `COMMITS: <sha>...` or `COMMITS: none`); workers never push, merge or create worktrees. Every line a worker changes traces to its task; it reports unrelated issues (dead code, bugs, style) instead of fixing them. Every sub-agent dispatch's `description` starts with its role slug and a colon: `builder: ` (coder, tester, docs, cleanup), `reviewer-spec: `, `reviewer-quality: `, `reviewer-minimalist: ` or `devils-advocate: ` (interrogate), so observers such as FlowObserve's Canopy read the role instead of guessing it. Use Codex sub-agents when available (independent tasks in parallel); otherwise do the tasks yourself, one at a time. Workers start on a cheaper model; `needs_stronger_model` or your judgment picks the stronger one, after `log_escalation`. Right after every dispatch, including retries and doing a task yourself, call `log_dispatch` (task as "<worktree branch>:<plan task id>", tier as the model name, role, attempt starting at 1).
6. **On return.** First run `"<dryas-py>" -X utf8 "<dryas-root>/jev/scope_audit.py" .orchestrate/PLAN.md <N> --base <base of N> <COMMITS shas>` in the worktree. `ok: false` means the task is not done: add the exact revert commands to `.orchestrate/approved.json` (`git checkout -- <path>` for each tracked file in `outside`; the gate denies discards during a run unless approved), then re-dispatch on the same model with "revert these files: <outside> (run exactly `git checkout -- <path>` if tracked, delete the file if new), then make the change with your edit tool inside your Scope". That re-run is not a climb; a second audit failure counts as a failure. `SCOPE: need <path> because <reason>`: you decide; if justified, add the glob to that task's Scope in `.orchestrate/PLAN.md`, then re-dispatch. `NEEDS DECISION: <command> because <reason>` means the gate denied a risky command and nobody is asked: you decide. Approve only when the command is needed for the task, stays inside the worktree, and can be undone or only touches generated or test data: add `{"cmd": "<exact command>", "task": "<N>", "reason": "<one line>"}` to `.orchestrate/approved.json` (`{"commands": [...]}`; create it if missing), call `log_override` (question "run_ask", Jev "ask", yours "allow", the reason) and re-dispatch. After writing `approved.json`, run the audit (or `scope_audit.py` with no shas) and keep its `approved_sha`; pass `--approved-sha <it>` on every later audit. Before the first approval, pass the sha of the empty file shown in the first audit output. A mismatch means someone other than you changed the approvals: treat the task as failed, restore your version, and report it in the end report. Otherwise re-dispatch with a safer way, or make it a `NEEDS USER` item: the task stays not done, its id leaves `active.json`, and the run carries on. The gate never lets `approved.json` cover a push, a deploy or cloud command, or a delete outside the worktree: only an exact entry in the plan's Risky actions can. Then check each Done criterion against the report. A failure is retried once on the same model, then moved to the stronger model (`log_escalation` with task, reason, decided_by, from_model, to_model). If the strongest model fails too, stop and report to the user. Store each outcome with `memory_store` (server `jev`).
6a. **Task review and usage (for step 5).** Before writing `.orchestrate/active.json`, run `"<dryas-py>" -X utf8 "<dryas-root>/jev/task_review.py" answer .orchestrate/PLAN.md <N>` for each task; write the file as `{"active": [<ids>], "review_version": 1, "review": {"<N>": <that task's "entry">}}` (only you write it; Codex workers carry no worker identity, so the scope lock cannot tell them from the main session; `review.task_skip` is never enforced for them). Keep the model choice of step 5 unless `dispatch.scored_tier` is true: then start on the entry's `tier`. Every dispatch-time `log_dispatch` of the task also passes the answer's score, score_tier and task_type. When the sub-agent returns, call `log_dispatch` again with the same task, tier, role and attempt, phase "return", plus tokens and duration_ms when it reports its usage.

6b. **Root cause, review, cleanup.** Before moving a failed task to the stronger model, find the root cause (`$dryas:debug`; the rule is `<dryas-root>/pstack/principles/fix-root-causes.md`); a plan defect is fixed in the plan and retried on the same model (at most once per model; after that, move up). Start the next part only after every build task has left `.orchestrate/active.json`. Ask Jev `needs_interrogate` (noul: "Does the change described in `design_summary` and `diff_stat` restructure how components fit together, change an interface other modules depend on, or carry `contested: true`?"); if true at ≥ `interrogate.min_confidence`, the user asked, or the approved design marked the change contested, read `<dryas-root>/skills/interrogate/SKILL.md` (the `$dryas:interrogate` skill) and follow it. Then, unless the diff is documentation only, run one cleanup task on the diff's files following `<dryas-root>/pstack/cleanup.md`, tests rerun, before the review in step 7. Review and cleanup tasks (`Failing test first: none (review)` or `none (cleanup)`) skip the test-first step (item 4). When the approved design is performance work, tasks that report a measured number get the Done line `numbers vetted per <dryas-root>/pstack/benchmark-checklist.md`. When you give a worker its section, include the four principle lines from `<dryas-root>/pstack/principles/` (fix root causes, prove it works, test behavior, subtract before you add) in its prompt, plus one more line: before writing code, go down this ladder and stop at the first rung that works: YAGNI (is it needed at all?), reuse of code the repo already has, the language stdlib, a native platform feature, an existing dependency, a one-liner, and only then minimum new code.

7. **Finish.** If every task left is `NEEDS USER` or blocked, skip review and merge and go straight to the report. Delete `.orchestrate/active.json`. When the `## Lens` block in the spec named in the plan header (`**Spec:**` line of the plan the run was started from) has `Panel: design` or `Panel: design+product`, run `$dryas:lens` (design panel) on what was built before the review, in its § Inside /orchestrate mode: write `.orchestrate/<branch-slug>-lens.html` and name its path in the end report. Its `change` findings join the reviewers' findings. No `## Lens` block, no `Panel:` line, or `Panel: product`: no lens step. Review the worktree diff with `$dryas:review-request` (three-stage, reports kept separate) and handle findings with `$dryas:review-receive`; after each review round call `log_review` (task = the worktree branch, round, counts of critical, important and minor findings); then run `$dryas:verify`; then commit by reading `<dryas-root>/skills/commit/SKILL.md` and following its steps (the Claude edition reads commands/commit.md). Merge locally with `git merge --no-ff` only after review and verification; never push; call `log_merge` (task and branch = the worktree branch, tasks_merged = task sections in the plan, cost_usd if known); if it replies with a warning (no review recorded for the branch), tell the user. Role lessons, once per run after the merge: for each role that took part (`builder` when a build task ran, each review stage, `devils-advocate` when interrogate ran), store at most one lesson with `memory_store` (server `jev`), namespace `role-<slug>`, kind outcome, a one-line title and a body under 600 characters on what that role should do or avoid next time, taken from its review findings and escalations. Skip a role with nothing to learn. The tool tags the lesson with this repo and stores nothing when `memory.role_lessons` is off. Then remove the worktree. Name the harness (Codex) and the models used in the plan and the commit body.

   **Report, once.** Run `"<dryas-py>" -X utf8 "<dryas-root>/jev/run_report.py" <worktree> <run start from step 1b>`. Write the report in plain words first, for someone who does not code: how many parts are done; each part not done and why; each `NEEDS USER` item as a question with your recommended answer. Then a `Details` heading: the counts (`prompts` should be 0), commits, branch, files. Store one `memory_store` lesson (kind outcome) per recurring cause you saw; put proposals in the report, never apply them. End with the report; the harness shows it.
